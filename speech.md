## 1. Регулярные выражения: ошибки и новый синтаксис

Во втором докладе мы разбирали, что из современного JavaScript уже можно писать в проекте. Сегодня — регулярные выражения.

## 2. Две беды

С регулярками большинство работает редко. Задача понятная и без них: найти кусок текста, номер, почту, строку в логе. Шаблон один раз что-то находит, и внутрь никто не смотрит.

Вторая беда в том, как это ломается. Со стороны это не ошибка шаблона. В обоих случаях тест зелёный. На форме одна и та же строка срабатывает через раз. В другом месте в поле поиска вводят короткую строку, и вкладка зависает. Кажется, что сломалось что-то другое.

## 3. Кейс: поиск по логу тикета

В тикете лог переписки. По нему надо искать, подсвечивать найденное и доставать номера вроде T-10421.

На экране два сообщения. Мария пишет, что не открывается T-10421, и ставит большой палец. Иван просит проверить T-10421 и T-10422. В поле поиска человек может ввести что угодно.

## 4. test с /g срабатывает через раз

Человек ввёл текст в поле поиска. Функция отвечает, номер ли это тикета, вроде T-10421. Регулярка объявлена один раз снаружи функции и с флагом g. Функция вызывает у неё test. test проверяет, есть ли совпадение, и отвечает true или false.

На строке T-10421 три вызова подряд: true, false, true.

Флаг g нужен, чтобы найти много совпадений в одной длинной строке, а не чтобы проверять разные строки по очереди. Регулярка не знает, что следующий вызов получит новую строку. Она продолжает прежнюю и хранит место остановки в lastIndex.

После удачного поиска туда пишется позиция сразу за найденным куском. В T-10421 символы стоят на местах 0–6, сразу за ними позиция 7. Второй вызов открывает строку с сохранённой семёрки. На месте 7 символов уже нет, ответ false, и только тогда индекс сбрасывается в 0. Третий вызов снова с начала и снова true.

## 5. Почему так сделано

В log несколько номеров. Их надо найти и подсветить. Для этого цикл while крутит exec по одной и той же регулярке с флагом g.

Первый круг: exec ищет с lastIndex равным нулю, с самого начала. Находит T-10421, highlight подсвечивает его. Самое важное: сам exec ставит lastIndex сразу за найденным номером.

Второй круг: цикл заходит снова. exec берёт ту же регулярку, видит изменённый lastIndex и благодаря этому не застревает на первом номере. Ищет дальше по тексту, находит следующий, снова сдвигает lastIndex вперёд.

Когда все номера найдены и текст кончился, exec возвращает null, цикл завершается, lastIndex сбрасывается в ноль.

Тот же lastIndex крутит test с флагом g. Для обхода лога это удобно. Для проверки «номер ли это тикета» дважды подряд — ловушка с прошлого слайда.

## 6. Не смешивать /g и test

Нам не надо искать много номеров подряд. Нужно только понять, номер ли тикета ввели в поиск. Пишем test без флага g — между вызовами ничего не запоминается, второй раз снова true.

Если убрать g нельзя, после вызова поставьте lastIndex в ноль. Или объявите регулярку внутри функции: каждый вызов получит новый объект и начнёт с нуля.

Флаг g вместе с test в одной функции почти всегда лишний. Либо флаг не тот, либо на самом деле нужен exec или matchAll.

## 7. Деструктуризация match падает

Нужно вытащить из лога цифры номера. Одна строка: const [, id] = log.match(/T-(\d+)/). match ищет в логе T- и цифры. Скобки (\d+) как раз эти цифры. Запятая в [, id] пропускает целое T-10421 и кладёт в id то, что в скобках: 10421.

Если в логе нет ни одного T-…, match вернёт null. Из null цифры не достать — код выбросит TypeError.

На ревью это не заметят: строка короткая и выглядит нормально. В тесте если кладут лог с номером, null не поймают. Как починить — на следующем слайде.

## 8. Сначала проверка

Сверху на слайде остаётся ошибочная строка для сравнения. Под ней три копии той же строки. Стрелками они по очереди превращаются в правки.

Ошибка: const [, id] = log.match(/T-(\d+)/). Нет T-… — null, деструктуризация падает.

Первая правка: справа ?? []. Вместо null пустой массив, id будет undefined.

Вторая: log.match(...)?.[1]. Нет совпадения — сразу undefined, без TypeError.

Третья: тот же match, но сначала if (!match) return, потом const [, id] = match. Длиннее, зато проверка видна глазами.

Без запасного пути исходную строку в ревью лучше не пропускать.

## 9. Один флаг меняет форму match

Этот слайд объясняет подводный камень метода .match(), из-за которого можно легко сломать логику программы или запутаться в типах данных.
Здесь показано, как один и тот же метод .match() возвращает совершенно разные структуры данных в зависимости от того, добавили вы флаг /g или нет.

Без флага g вы просите первое совпадение и всё про него. На нашем логе: целиком T-10421, цифры из скобок 10421, index — с какого места в логе нашлось, и input — сам исходный лог. Так вытаскивают кусок из номера.

С флагом g вы просите все совпадения списком. Подробности не важны. На логе три номера: T-10421 у Марии, потом ещё T-10421 и T-10422 у Ивана. В ответе три строки целиком, без цифр из скобок, без index и без input. Движок их просто не отдаёт.

Один символ g в конце литерала молча меняет структуру. Без g во втором элементе массива лежат цифры 10421. С g во втором элементе уже другой целый номер T-10421. Ждали цифры из скобок — получили не то.

TypeScript разницы не видит: тип один, RegExpMatchArray или null. При написании ошибки не будет, упадёт уже в рантайме.

Нужны и все вхождения, и цифры из скобок — match с g не тот метод. Об этом следующий слайд.

## 10. Группы — у exec и matchAll

Если нужны все вхождения и группы, match с g не тот метод. Либо exec в цикле, и тогда помним про lastIndex. Либо matchAll — до него дойдём во второй части, он как раз снимает эту вилку.

Коротко: match без g — первое совпадение с группами. match с g — все совпадения, только текстом. Не оба сразу.

## 11. В поле поиска скобка, потом зависание

Обычный поиск: человек вводит строку в инпут, мы кладём её в new RegExp и фильтруем лог. Выглядит разумно — ищем буквально то, что написали. Без обработки ввода приложение можно либо уронить, либо намертво повесить.

Первое — SyntaxError. Человек ищет открывающую скобку. Для него это просто символ. Для конструктора скобка — начало группы. Он ждёт закрывающую, не находит и бросает ошибку. То же с [, ?, +. Сырую строку от пользователя в new RegExp класть нельзя.

Второе — ReDoS, катастрофический бэктрекинг. На слайде шаблон (a+)+$: плюс внутри плюса. Строка из пары десятков «a» и в конце другой символ. Движку нужно перебрать, как разрезать эти «a» на повторы. Число комбинаций растёт экспоненциально. На 20–30 символах вкладка зависает. На Node процессор уходит в 100%, сервер перестаёт отвечать другим запросам.

Так получается не только из учебника. К пользовательскому вводу дописывают плюс или звёздочку, или сами пишут «один или больше кусков, в каждом один или больше символов». На слайде только вид шаблона. Живым гонять не будем: зависнет и эта вкладка.

## 12. Ввод не класть в шаблон сырьём

От падения — экранировать ввод, чтобы скобка осталась скобкой. Штатный способ — RegExp.escape. Метод уже в стандарте, свежие браузеры его умеют. В нашем defaults ещё Chrome 109: без полифила получите RegExp.escape is not a function. Раньше копировали функцию со StackOverflow, часто без дефиса или слэша. Как устроен штатный метод — во второй части.

От зависания — не вкладывать плюс в плюс и звёздочку во что угодно: (a+)+, (\w+)*. Это вложенные квантификаторы, на прошлом слайде из‑за них и зависало.

Если нужен просто текст, без масок — string.includes. Нет компиляции шаблона, нет спецсимволов, на коротком поиске это обычная проверка строки, а не тяжёлый объект RegExp. Длину строки в поле поиска тоже можно ограничить. Ссылки на regex101 и recheck — в конце.

## 13. Подсветка режет эмодзи пополам

В нашем логе у Марии стоит большой палец. Без флага u регулярка смотрит кодовые единицы UTF-16, не символы. У 👍 две единицы, length — 2.

Точка без u берёт одну единицу. Шаблон ^.$ ждёт ровно одну и конец строки — на целом пальце false.

Квадратные скобки без u ещё хуже: 👍 внутри [ ] движок режет на две половинки и ищет «либо первую, либо вторую». Целый палец не совпадает. Одна суррогатная половина — совпадает. Ошибки SyntaxError тут нет, просто молча не то.

Если подсветка режет по index и длине такого совпадения, в интерфейсе кракозябра, соседние символы съезжают.

## 14. Флаг u

Флаг u — смотреть символами. Точка берёт весь палец, скобки тоже. Для номеров тикетов разницы не видно. Для лога с эмодзи — видна сразу.

Этого флага достаточно, чтобы не резать символ пополам. Во второй части — флаг v и \p{Emoji}: составные эмодзи и свойства вместо самодельных диапазонов. Сейчас хватает u.

## 15. replace без /g меняет первое

Подсветка через replace: на место номера ставим mark. В строке замены $& — это найденный текст целиком, встроенный в JS способ сказать «подставь то, что только что нашёл».

Без флага g replace отработает молча: заменит строго первое T-10421. В логе два номера, на экране подсвечен один. Классический визуальный баг, его легко пропустить в тестах.

Логично подумать: нужны все вхождения — возьму replaceAll. Но replaceAll с регуляркой без g не молчит: код упадёт с TypeError.

Так сделано намеренно. Когда добавляли replaceAll, хотели защитить от случайной ошибки: метод называется «заменить все», значит при регулярке флаг g обязан быть явным. Забыли — движок бьёт ошибкой сразу, а не делает вид, что всё нормально.

Правило: replace без g — тихо только первое. replaceAll с регуляркой — только с g, иначе TypeError.

## 16. Доллар в строке замены

Второй аргумент replace — не всегда буквальный текст. Это особый шаблон: $& — целое совпадение, $1 — то, что в первых скобках, $$ — буквальный доллар. Если туда попадает произвольный пользовательский текст, эти последовательности в нём сработают.

Без скобок в регулярке $1 часто остаётся текстом «$1» — порчу не видно. Со скобками /T-(\d+)/g и note равным '$1' вместо текста подставятся цифры номера. В админке с массовой заменой модератор пишет Cost: $1, а в базу улетают битые данные.

Если строка для замены пришла из инпута, конфига или API и должна вставиться буквально — передавайте функцию: () => note. Движок возьмёт результат функции и не будет разбирать доллары внутри. Можно заранее заменить $ на $$, но функция чище.

## 17. Точка не берёт перевод строки

Точка — не любой символ. По умолчанию это любой символ, кроме перевода строки. Чтобы показать флаг s, начало и конец шаблона должны стоять на разных строках лога. /T-10421.*T-10422/ на нашем логе и без s даёт true: оба номера в одной строке Ивана, переноса между ними нет. А «пишет» у Марии и «Иван» — уже на разных строках: /пишет.*Иван/ без s — false, точка спотыкается на \n. С флагом s — true.

Флаг m сюда не поможет. Его часто ставят «потому что текст многострочный», но зоны ответственности разные. s управляет точкой. m управляет якорями ^ и $: без m это края всего текста, с m — начало и конец каждой строки внутри. Время в начале строки лога — флаг m. Кусок текста через перенос — флаг s.

## 18. Жадный и ленивый

Звёздочка по умолчанию жадная: берёт как можно больше, лишь бы остаток шаблона ещё нашёлся. На слайде с флагом s, чтобы .* мог перейти через перевод строки — это как раз прошлый слайд.

Жадный /T-.*\d+/s на нашем логе от первого T- добежит почти до конца, а потом пятится назад, пока хвост \d+ не сядет на последнюю цифру. В совпадение попадут оба номера, текст между ними и палец. Ленивый /T-.*?\d+/s делает маленькие шаги и останавливается на первом же номере: T-10421.

На короткой строке с одним тикетом оба варианта совпадают, поэтому в тестах всё зелёное. На реальном логе подсветка сжирает полсообщения. Если выделение захватило лишнее — первым делом ищите жадный .* или .+ и делайте их ленивыми.

Статусы те же, что во втором докладе. Смотрим наш defaults, в нём ещё Chrome 109, и обязаны с этим считаться. Используем — браузеры из списка, включая 109, уже умеют из коробки. С полифилом — новый метод, полифил короткий, кладём и пишем. Не пишем — новый синтаксис, которого в 109 нет, а Babel или SWC сами его в старый код не перепишут. ## 20. matchAll

Помните слайд про две формы match: без g — детали одного совпадения, с g — все совпадения, но без цифр из скобок. matchAll снимает этот компромисс: все вхождения, и на каждом шаге и совпадение, и скобки, и index.

Вместо while с exec пишем for (const match of log.matchAll(/T-(\d+)/g)). Итератор сам шагает по логу. На слайде регулярка — литерал: каждый вызов создаёт новый объект, lastIndex всегда с нуля. Если передать ту же «живую» константу с /g, у которой lastIndex уже не ноль, matchAll начнёт не с начала — это всё ещё общая ловушка. Но сам обход уже не надо крутить руками и не надо сбрасывать индекс между шагами цикла.

Флаг g обязателен: без него сразу TypeError, как у replaceAll. Баг не маскируется. Метод с 2020-го, в нашем defaults включая Chrome 109 есть. Используем. Без полифила.

## 21. Флаг d

Для подсветки мало знать, что нашлось «T-10421». Нужны границы в логе: с какого символа по какой вырезать кусок. Раньше для целого совпадения считали руками: index плюс длина. Для цифр из скобок — ещё хуже: indexOf внутри совпадения. Если 10421 встречается дважды или совпадает с куском рядом, indexOf вернёт не то место.

Флаг d — hasIndices. У совпадения появляется indices: пары [start, end]. indices[0] — весь T-10421, indices[1] — только то, что в первых скобках. Координаты сразу под slice и substring: верхняя граница не входит в отрезок, единицу вычитать не надо. На matchAll с флагами gd берём пару и собираем лог: до совпадения как было, кусок в mark, дальше снова текст.

В Chrome с 90-го, в нашем 109 уже есть. Используем. Без полифила.

## 22. Именованные группы

Обычные скобки читают по порядку: match[1] — то, что в первых скобках, match[2] — во вторых. Было /T-(\d+)/, цифры в match[1]. Переписали на /(ticket )?T-(\d+)/ — перед номером появились новые скобки, цифры съехали в match[2]. Старый код всё ещё читает match[1], там уже не номер тикета. Парсинг и подсветка ломаются в неожиданных местах.

Именованная группа: T-(?<id>\d+). Имя прямо в шаблоне. Дальше match.groups.id — цифры по ключу, сколько скобок вокруг ни добавь. В замене то же имя: '/tickets/$<id>', не надо считать, третья это группа или четвёртая.

Если совпадения нет, match будет null, и match.groups.id упадёт. Безопаснее: const { id } = match?.groups ?? {}. Если совпадение есть, а эта именованная группа в необязательной части не сработала, id будет просто undefined — без TypeError.

С флагом d из прошлого слайда координаты тоже по имени: вместо match.indices[1] пишем match.indices.groups.id. Магических чисел в коде больше нет.

С 2018 года, в нашем списке давно. Используем. Через полгода шаблон всё ещё читается.

## 23. Lookbehind

Часто нужны цифры строго после T-, а сам префикс в результате не нужен. Раньше городили T-(\d+) и брали match[1], либо резали строку slice после match.

Lookbehind: (?<=T-)\d+. Движок находит цифры, смотрит налево: там T-? Если да — совпадение засчитывается. Сам префикс в результат не входит: это проверка, не захват. Поэтому match[0] сразу '10421', а не 'T-10421'.

Негативный вариант нужен, когда ищем числа не из тикетов: времена 14 и 02, суммы, другие id. Наивный (?<!T-)\d+ врёт: на T-10421 движок пропускает T-1 и забирает хвост 0421. В ответе будут и времена, и обрубки номеров.

Правильнее \b(?<!T-)\d+: граница слова не даёт врезаться внутрь номера. Или (?<!T-\d*)\d+ — lookbehind переменной длины, в JS так можно, во многих языках нельзя.

Lookahead у JavaScript был всегда, lookbehind — с 2018-го. В нашем Chrome 109 есть. Обходные пути с группами и slice больше не нужны. Используем.

## 24. RegExp.escape

Помните слайд, где сырой query в new RegExp ломал поиск на одной скобке. Теперь в языке есть официальный ответ: RegExp.escape. Оборачиваем ввод: new RegExp(RegExp.escape(query), 'gi'). Скобка, точка, плюс и звёздочка становятся обычным текстом, а не синтаксисом шаблона.

Раньше в каждом проекте жила самодельная escapeRegExp со StackOverflow на replace. В ней то и дело забывали дефис или слэш. На буквах поиск работал, на хитром символе снова падал. Стандартный метод закрывает крайние случаи спецификации, которые ручная замена слэшем не закрывает.

Это метод, не новый синтаксис внутри /.../ — его можно безопасно полифилить. В современных браузерах с Chrome 136, в нашем defaults ещё Chrome 109. Статус: с полифилом. Полифил лёгкий. Как с toSorted во втором докладе: замерить размер сборки, подключить и писать современный безопасный код.

## 25. Флаг v

Флаг v — наследник u. Плюс операции над множествами символов: пересечение, разность — например, все латинские буквы кроме гласных. И нормальная работа с составными эмодзи.

Обычный палец вверх — одна суррогатная пара, u с Extended_Pictographic справляется. А эмодзи программиста или повара — цепочка из нескольких символов, склеенных невидимым соединителем. u часто сматчит только первый кусок и «распилит» картинку. v с RGI_Emoji — Recommended for General Interchange — берёт всю картинку целиком: это набор эмодзи, которые Юникод рекомендует показывать как одну целую.

v нельзя смешать с u в одном литерале: либо /u, либо /v. v умеет всё полезное из u и ещё множества.

В Chrome с 112-го. В нашем defaults ещё 109. Это синтаксис литерала, не метод вроде RegExp.escape. Chrome 109 наткнётся на /v и выбросит ошибку разбора. Babel умеет сам переписать ?? или ?., но для флага v стандартного preset-env мало — нужен отдельный плагин. Пока плагина в сборке нет — не пишем. Не процент с caniuse, а этот факт.

## 26. Модификатор внутри выражения

Флаги вроде i обычно на всю регулярку. А задача гибридная: префикс T- строго заглавный — маленькая t- это ошибка, — а слово «проверь» пользователь пишет как угодно: ПРОВЕРЬ, проверь, Проверь.

Если включить /i на всё, сквозь валидацию пролетит и t-10421. Если не включать — руками городить [Пп][Рр][Оо]… Шаблон становится нечитаемым адом.

(?i:проверь) включает регистронезависимость только внутри скобок. В /T-\d+.*(?i:проверь)/ префикс T- остаётся чувствительным к регистру, слово — нет. Можно и выключать: (?-i:...) внутри зоны, где глобальный i не нужен.

В Chrome с 125-го. В нашем 109 нет. Это синтаксис литерала, как флаг v: без отдельного плагина сборка не перепишет, старый браузер выбросит SyntaxError. Не пишем. Пример на слайде — задел на будущее, чтобы не изобретать велосипед, когда список догонит или появится плагин.

## 27. Свойства юникода

Раньше «любая буква» писали [a-zA-Z] — кириллицу, умлауты и иероглифы такой диапазон не берёт. Для эмодзи тащили простыни шестнадцатеричных диапазонов из интернета, на ревью их никто не проверял.

Теперь категории из Юникода: \p{Letter} — любая буква. Для картинок вроде пальца — \p{Extended_Pictographic}. Здесь ещё одна грабля: \p{Emoji} звучит правильно, но в это свойство входят и цифры 0-9, # и * — из них собирают эмодзи вроде 1️⃣. На нашем логе log.match(/\p{Emoji}/u) первым находит '1' из времени 14:02, а не 👍. Extended_Pictographic вернёт палец.

Критично: нужен флаг u или v. Без него \p — не свойство. Движок часто читает это как обычную букву p плюс скобки: шаблон ищет буквально p{Letter}, а не буквы. Ошибки может не быть — просто тихо не то. С флагом u в нашем списке с 2018 года. Используем.

Составные эмодзи с семьёй и цветом кожи — уже история флага v и \p{RGI_Emoji}. Для одиночного пальца в логе хватает u и Extended_Pictographic.

## 28. Один поиск

Соберём функцию highlight(log, query). На слайде стрелками: было → промежуточный шаг → итоговый код.

Старый вариант выглядит безобидно, а в нём все мины доклада сразу. Сырой query в new RegExp — скобка, и SyntaxError. replace без g — в логе два тикета, подсвечен один. Нет флага u — эмодзи режет пополам. И const [, id] = log.match(...): если в логе нет T-…, match вернёт null, деструктуризация выбросит TypeError.

Первый шаг: в начале if (!query) return log — иначе RegExp.escape('') даст пустой шаблон, и mark встанет между каждыми двумя символами. Дальше RegExp.escape и replace с функцией и флагом gu. Скобка больше не ломает поиск, подсвечены все вхождения, эмодзи целый. Лишний match с деструктуризацией убираем — для подсветки query он не нужен.

Итог: флаги gdu, обход через matchAll, границы из indices, сборка строки через slice. matchAll всегда отдаёт итератор: даже если совпадений нет, цикла просто не будет — без TypeError. lastIndex не крутим руками, ввод не ломает шаблон.

Это не восемь фич подряд. Это одна функция, в которой старые костыли больше не нужны.

## 29. Ссылки

Если заберёте с доклада три правила — уже закроете большую часть сегодняшних багов.

Первое: не мешайте /g и test, когда проверяете строки подряд. Второе: не деструктурируйте match вслепую — без совпадения будет null и TypeError. Третье: не кладите сырой ввод в new RegExp без экранирования.

Остальное — в закладки. regex101: отладить шаблон и посмотреть счётчик шагов — если шагов слишком много, регулярку пора упрощать. recheck: прогнать тяжёлый шаблон на ReDoS, прежде чем отдавать на бэкенд. MDN: синтаксис и даты в браузерах, отдельно страница RegExp.escape. caniuse и npx browserslist — как во втором докладе: зелёный процент «в мире» не ответ, пока не сверите со своим списком, где у нас ещё Chrome 109.

Пишите безопасные регулярки, берите то, что уже можно в defaults, и не режьте интерфейс на эмодзи. Спасибо.
